# Platform

Canonical memory for development environment, browser targets, PWA behavior,
runtime capability tiers, and hosting assumptions.

## Current targets

- Development and first validation: local Apple M3 MacBook with macOS Chrome.
- Primary runtime target: Android Chrome.
- Optional targets: Linux AMD64 Chrome and iOS Chrome or installed PWA, each
  requiring separate validation.
- Intended hosting target: GPT Sites.
- The application is assumed to be static or mostly static unless hosting
  evidence establishes a necessary backend capability.

## Browser and PWA expectations

The intended browser architecture may use:

- React, TypeScript, and Vite;
- Web Audio API and AudioWorklet;
- Web Workers;
- WebAssembly;
- IndexedDB or OPFS;
- Service Worker;
- optional WebGPU.

The PWA should support installation where available, offline lesson access
after download, local progress, separately cached recognition models, an
explicit model-download flow, recovery after browser cache eviction, and clear
microphone-permission handling.

Heavier audio and recognition work should run outside the main UI thread.

Candidate interaction state:

```text
idle
→ playing reference
→ recording
→ evaluating
→ passed or failed
→ next repetition
```

Candidate responsibility boundary:

```text
UI
→ audio capture
→ runtime adapter
→ recognition output
→ scoring engine
→ feedback visualization
```

## Device constraints

### macOS Chrome

- Expected capabilities include microphone access, AudioWorklet, workers,
  WebAssembly, persistent browser storage, service workers, PWA installation,
  and WebGPU on supported configurations.
- M3 performance is the first baseline but must not be treated as
  representative of mobile hardware.

### Android Chrome

Important unknowns include variable memory limits, thermal throttling, model
download and initialization time, device-dependent sample rates, microphone
interruptions, tab suspension, limited background execution, and storage
eviction.

### Linux Chrome

Likely standards-compatible, but microphone permissions/devices, Japanese
system voices, WebGPU drivers, PWA behavior, and storage quotas remain untested.

### iOS

Chrome on iOS must not be assumed to behave like desktop or Android Chrome.
WebAssembly performance, WebGPU, AudioWorklet, microphone capture, service
workers, persistent storage, model caching, memory limits, and PWA lifecycle
all require separate checks. A limited local tier or explicitly optional remote
scorer may be needed, but no remote dependency is currently assumed.

## Capability-tier hypothesis

- Tier A: WebGPU and sufficient memory/storage; full local recognizer plus
  acoustic alignment and visualization.
- Tier B: WASM CPU and sufficient memory for a small recognizer; reduced
  concurrency or slower evaluation.
- Tier C: insufficient recognizer resources; basic recording quality, timing,
  and reference comparison without detailed pronunciation claims.

Runtime capability detection is preferred over device-name checks. The selected
tier should be communicated clearly.

## Unverified GPT Sites assumptions

- static asset size limits;
- efficient large-model delivery;
- cache-control behavior;
- MIME types for WebAssembly and model files;
- configurable cross-origin isolation headers;
- service-worker support;
- deployment and cached-update behavior.

## Active platform gates

- Confirm stable microphone PCM capture and repeated play/record behavior in
  local macOS Chrome.
- Measure the chosen local recognizer on the M3, then on representative Android
  devices.
- Confirm that a WASM CPU path is usable before treating WebGPU as an
  enhancement.
- Verify GPT Sites model delivery, caching, headers, service workers, and update
  behavior before fixing the deployment architecture.
