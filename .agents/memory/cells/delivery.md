# Delivery

Canonical memory for local preview, development QA, release packaging, and
deployment gates.

## Current direction

- Develop and host the application locally for routine preview.
- A successful build does not authorize deployment.
- Deploy only the exact source and packaged artifact that completed the agreed
  automated tests and manual QA.
- The user is currently the only application user. Prefer one deployable
  codebase and a lightweight local workflow over staging infrastructure.

The intended flow is:

```text
develop locally
→ run reproducible QA
→ preview the exact build locally over trusted HTTPS
→ explicit approval
→ deploy that exact artifact privately
```

QA and deployment are separate actions. Deployment must not rebuild or
substitute a different artifact after approval.

## Minimum sufficient QA and release workflow

1. Keep the deployable site in an isolated Git project that cannot inherit the
   parent repository's private voice-data history.
2. Provide hot-reload development and a production-build local preview.
3. Provide one reproducible local QA command covering type checks, lint, unit
   tests, build, browser smoke tests, forced WASM fallback, optional WebGPU,
   and deployment-artifact privacy checks.
4. Perform explicit real-device QA over trusted local HTTPS for microphone and
   runtime behavior.
5. Freeze the QA-passed commit and packaged artifact and record their
   checksums.
6. Save an immutable Sites version from that exact source state.
7. Deploy privately only after explicit QA sign-off.

CI is optional in the current minimalist phase. A trustworthy local QA command
plus a separate manual deployment action is sufficient.

The package check must reject recordings, datasets, secrets, training
artifacts, development-only fixtures, captured screens, and private debug
data.

## Single-user boundaries

Do not add these without a proven need:

- separate development and production branches;
- a staging site or environment-promotion machinery;
- multiple user roles;
- a separate QA database.

Prefer browser-local storage plus export/import when it satisfies the product.
Keep hosted storage only when cross-device synchronization or another proven
server-side requirement justifies it.

## Agent preview and debugging authority

- Coding agents may start or reuse the normal local client host, open the exact
  URL it reports, inspect runtime behavior, and debug without separate
  per-run permission.
- Headless checks may use OpenCLI, Playwright, Puppeteer, direct CDP, or another
  conventional framework. Real-browser control may be used for visual,
  interaction, permission, WebGPU, audio, and browser-specific checks.
- Prefer fake or synthetic media for automated checks.
- This authority does not include ambient microphone or camera capture,
  private-data upload, external publication, or deployment.
- Starting or testing the client never satisfies or bypasses the explicit
  deployment gate.

## Development-only navigation and capture

- During development and QA, provide programmatic navigation to every screen
  and relevant UI state.
- Support viewport and full-page screenshots for visual evidence and
  regression comparison.
- Make the harness usable through headless frameworks and real-browser control.
- Put debug routes, deterministic fixtures, state seeding, navigation controls,
  and capture hooks behind an explicit development/QA flag.
- Disable the harness for deployment and exclude private debug surfaces and
  fixtures from the production artifact where practical.
- For local headless screenshots in the current environment, the Playwright
  package may request a newer cached `chromium_headless_shell` than is
  installed. Launching Playwright with `{ channel: "chrome" }` uses the
  installed Google Chrome and has worked for screenshots and click-through QA.
- `?qa=1` exposes the PoC's synthetic success, near-miss, and failure controls.
  Headless Chrome may stall on speech autoplay when no TTS voice is available;
  use the one-bubble Skip control to reach a learner-speaking state.
- Use the exact port reported by the normal development server. Port `3001`
  was used once because `3000` was already occupied; this is not a new default
  and does not authorize port scanning.
- Browser evaluation scopes used for read-only QA may not expose every web API.
  A `caches.keys()` inspection failed with `caches` undefined; that is a tool
  limitation, not an application failure. Verify service-worker precaching by
  served responses, source inspection, or a real offline reload instead.
- Direct `file://` navigation to repository HTML such as
  `.agents/resources/seinen-manga-frame/mock.html` is blocked by browser
  security policy. Read such references as files, or serve them, rather than
  working around the block.
- Browser-control viewport resizing through the Chrome extension can silently
  no-op. The transition worktree successfully exercised real `412×915` media
  queries through a same-origin iframe; the selector worktree later used the
  browser viewport capability directly.
