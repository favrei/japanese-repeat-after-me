# Product and Technical Discussion

## 1. Product concept

The application is a Japanese speaking-practice tool built around repeated pronunciation exercises.

The primary learning loop is:

1. The application presents a Japanese sentence.
2. The learner listens to a reference recording.
3. The learner repeats the sentence.
4. The application evaluates the recording.
5. The learner must successfully repeat the sentence a configurable number of times.
6. The next sentence is unlocked after the required successful repetitions.

The application should not only return a pass or fail result. It should also indicate which parts of the sentence were probably missing, mistimed, unclear, or substantially different from the target.

## 2. Product positioning

The initial product is a focused Japanese speaking-drill engine rather than a complete language-learning platform.

Its main value is:

- repeated speaking practice
- immediate automatic verification
- localized feedback
- configurable mastery requirements
- user-generated content
- low operating cost

Grammar courses, social features, teacher marketplaces, open-ended conversation, and full curriculum design are outside the current scope.

## 3. Content generation

Learning content is generated by AI, but the user is responsible for providing access to the AI system or importing content generated elsewhere.

Possible approaches include:

- copying a provided prompt into an AI assistant
- importing generated JSON
- optionally connecting a personal API key later
- importing sentence lists created elsewhere

A lesson item should contain at least:

```json
{
  "text": "今日は天気がいいですね。",
  "reading": "きょうはてんきがいいですね。",
  "translation": "The weather is nice today.",
  "difficulty": "beginner",
  "requiredSuccesses": 5,
  "notes": [],
  "tags": ["weather", "daily conversation"]
}
```

The generated reading should be validated before it becomes the pronunciation target.

## 4. Application architecture

The application is intended to be a Chrome-first Progressive Web App.

Candidate frontend technologies:

- React
- TypeScript
- Vite
- Web Audio API
- AudioWorklet
- Web Workers
- IndexedDB or OPFS
- Service Worker

A possible interaction state machine is:

```text
idle
→ playing reference
→ recording
→ evaluating
→ passed or failed
→ next repetition
```

Recognition and heavier audio processing should run outside the main UI thread.

## 5. Recognition problem

The application does not require unrestricted speech transcription.

Because the expected sentence is already known, the problem is narrower:

> Did the learner pronounce the expected sentence, and where did the attempt diverge from the target?

This is target-conditioned pronunciation assessment rather than general-purpose ASR.

A conventional recognizer may still be used as one signal, but the final result should not depend only on its decoded transcript. A language model can infer the intended sentence even when pronunciation is weak.

## 6. Local-first recognition

A fully client-side Chrome implementation is considered viable for an initial product experiment.

A candidate pipeline is:

```text
microphone
→ voice activity and audio-quality checks
→ lightweight Japanese recognition
→ constrained comparison with the expected sentence
→ acoustic alignment
→ localized feedback
```

This avoids per-attempt cloud API fees. The recurring infrastructure cost can be limited mainly to static hosting and model-download bandwidth.

## 7. Acoustic comparison

Recognition may be supplemented by direct acoustic comparison between a reference recording and the learner recording.

```text
reference audio → acoustic features
learner audio   → acoustic features
                 ↓
        dynamic time warping
                 ↓
      aligned sentence regions
```

Candidate features include:

- MFCC
- log-mel spectrograms
- pitch contour
- energy
- speech-model embeddings

This may help detect:

- skipped regions
- unusually long pauses
- incorrect timing
- long vowels that are too short
- small っ timing errors
- strongly different sound regions

Direct comparison with one TTS voice cannot be treated as a precise linguistic diagnosis because speakers naturally differ in pitch, voice quality, and timing.

## 8. Scoring

The system should expose several dimensions rather than one unexplained score.

Possible dimensions include:

- completeness
- sentence match
- pronunciation confidence
- timing
- rhythm
- long-vowel correctness
- pause placement

Example output:

```json
{
  "passed": false,
  "overallScore": 0.76,
  "completeness": 0.94,
  "timing": 0.81,
  "units": [
    {
      "text": "きょ",
      "score": 0.92,
      "status": "correct"
    },
    {
      "text": "う",
      "score": 0.44,
      "status": "needs_attention",
      "issue": "long vowel may be too short"
    }
  ]
}
```

Initial feedback should be described as an estimate, not a definitive phonetic judgment.

For beginners, the pass condition should emphasize:

- completeness
- expected order
- avoidance of major substitutions
- important Japanese timing distinctions

Pitch accent and natural rhythm should initially be coaching information rather than mandatory pass criteria.

## 9. TTS

Reference audio can be provided through browser or operating-system TTS without recurring service cost.

Advantages:

- no server requirement
- immediate availability
- simple integration

Limitations:

- voice quality differs by device
- Japanese voices may not be installed
- pronunciation and pitch accent may vary
- the same lesson may sound different across platforms

Imported or pre-generated audio can be supported later for consistent reference pronunciation.

## 10. Cross-platform model deployment

A shared model format is preferred.

ONNX is a candidate because it can be used through:

- ONNX Runtime Web in Chrome
- ONNX Runtime on Android if a native wrapper is later introduced
- ONNX Runtime on macOS and Linux
- server-side ONNX Runtime as an optional fallback

The architecture should separate:

```text
UI
→ audio capture
→ runtime adapter
→ recognition output
→ scoring engine
→ feedback visualization
```

The initial scoring engine may be written in TypeScript. Performance-sensitive components could later be implemented in Rust or C++ and compiled to WebAssembly.

## 11. Longer-term custom model

An existing lightweight recognizer may be sufficient for validating the product loop, but it may not provide reliable mora-level assessment.

A later model could contain:

- a compact Japanese speech encoder
- kana or phoneme outputs
- constrained alignment against the expected sentence
- pronunciation-quality scoring

The main research risk is calibration on non-native Japanese speech. Native-speech ASR data alone may not teach the system which learner errors should be accepted, rejected, or explained.

## 12. Existing products and differentiation

Related products include shadowing applications, sentence-repetition systems, and language-learning applications with pronunciation checks.

The concept is therefore not entirely new.

Potential differentiation includes:

- user-generated lesson packs
- configurable repetition requirements
- fully local verification
- no mandatory subscription
- transparent localized feedback
- provider-independent content generation
- offline use

The strongest differentiator would be useful sentence-level or mora-level feedback rather than a generic correct or incorrect result.

## 13. Current technical position

A free, local Chrome version appears feasible as a product experiment.

A reasonable initial configuration is:

```text
Chrome PWA
+ local Japanese recognition model
+ WebAssembly or ONNX Runtime Web
+ acoustic feature extraction
+ dynamic time warping
+ constrained matching against the expected sentence
+ local model and lesson caching
```

This will not provide perfect phonetic diagnosis, but it may be sufficient to evaluate the central product question:

> Will learners repeatedly practise a sentence when the application gives immediate approximate feedback and requires several successful attempts?

## 14. Scope boundary

This document records the current concept, candidate technologies, limitations, and discussion points. It is not an implementation schedule or delivery plan.
